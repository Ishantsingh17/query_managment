DOCUMENT 01 — PRD
PRODUCT REQUIREMENTS DOCUMENT

Project: Automated Audit Evidence Retrieval
Version: 1.0
Status: Draft for implementation

1. APP NAME
Automated Audit Evidence Retrieval

2. TAGLINE
Turn an auditor’s natural-language request into a validated evidence package.

3. PROBLEM
Audit teams spend manual effort locating, extracting, compiling, validating, and sharing evidence across different business systems and repositories. The four selected POC use cases have repetitive retrieval and preparation activities, but differ in their required inputs, evidence, and human involvement.

The POC will demonstrate an agentic workflow that:
- Accepts an auditor’s natural-language request.
- Understands and classifies the request into one of four supported use cases.
- Extracts the search parameters from the request.
- Determines the required evidence from a controlled requirement catalog.
- Searches configured SQLite mock databases sequentially through an MCP layer.
- Retrieves matching data/documents.
- Stores retrieved evidence in a request-specific staging area.
- Validates completeness and basic matching.
- Re-checks/retries missing evidence where possible.
- Generates an audit evidence package.
- Routes the package to an AP reviewer before final response.

4. TARGET USERS

Primary: Auditor / Audit Team
The auditor knows the audit requirement and may provide values such as period, SOB, NAC range, report type, account, vendor, invoice number, or sample information. The auditor should not need to know database names, SQL, or storage locations.

Secondary: AP Reviewer / Audit Operations Reviewer
The reviewer checks the retrieved evidence package and validation summary before the package is finalized.

5. CORE VALUE PROPOSITION
- Natural-language audit request intake.
- Structured query understanding using Groq LLM.
- Controlled support for four POC use cases.
- Predefined use-case-to-required-evidence mapping.
- Multi-database sequential search instead of hard-coded evidence-to-system mapping.
- Retrieval Agent for search coordination and missing-evidence tracking.
- MCP layer for standardized database-search tools.
- Evidence staging and traceability by request ID.
- Basic validation and bounded retry.
- Reviewable, audit-ready output package.

6. SUPPORTED POC USE CASES

UC-01 — Cost Drill / Expense Drill Requirement
Inputs:
- Period
- SOB
- NAC Range
- Report Type

Required data/documents:
- GL Dump / Expense Ledger
- Trial Balance
- Cost Drill Reports: AP, AR, Others
- NAC Range Details
- Period Details

Current SOP:
1. Audit team sends request by email.
2. AP team raises request/ticket to GL R12 Support.
3. GL Support extracts cost drill data from Oracle.
4. AP validates period/NAC completeness.
5. Files are uploaded to auditor shared location.
6. Auditors are notified.

POC automation:
Parse inputs → identify UC-01 → load required evidence → search mock databases → retrieve reports/data → validate period/SOB/NAC/report type → stage → package → reviewer.

UC-02 — Schedules Requirement
Inputs:
- Account(s)
- Period
- Schedule type where applicable

Required data/documents:
- Ledger Extract
- Opening Balance
- Movement/Additions/Adjustments
- Closing Balance
- Ageing Details
- Long Outstanding Balance Explanations

Current SOP:
1. Extract ledger balances.
2. Prepare account-wise schedules.
3. Generate ageing analysis.
4. Collect explanations for unusual/long outstanding balances.
5. Prepare audit-prescribed format.
6. Upload and notify.

POC automation:
Retrieve/prepare data → calculate or assemble schedule → generate ageing → identify long outstanding items → flag explanation as human-required → finalize package.

UC-03 — Trade Payables Balance Confirmation Samples
Inputs:
- Vendor/sample list
- Period
- Available vendor/account identifiers

Required data/documents:
- Vendor-wise Payable Balances / APTB
- Ageing Report
- Balance Confirmation Letters
- Vendor Contact Details
- Outstanding Invoice Details

Current SOP:
1. Extract APTB and ageing.
2. Prepare confirmation letters.
3. Route for signatory approval.
4. Share approved confirmations.
5. Provide invoice-level ledger extracts.
6. Share vendor contact/communication information.

POC automation:
Parse sample inputs → retrieve balances/ageing/vendor data → generate confirmation letters → represent approval routing → package documents → reviewer.

UC-04 — Balance Confirmation Alternate Testing
Inputs:
- Vendor
- Invoice number(s)
- Invoice-level outstanding detail when provided

Required documents:
- Invoice Copies
- Purchase Orders (PO)
- GRN / Goods Receipt Note
- SES / Service Entry Sheet
- Supporting Documents

Current SOP:
1. Identify vendors with no confirmation.
2. Obtain invoice-level outstanding details.
3. Retrieve Invoice/PO/GRN/SES from ERP or repositories.
4. Compile supporting evidence.
5. Share evidence package.

POC automation:
Parse vendor/invoice → identify UC-04 → load evidence checklist → search all mock databases sequentially → retrieve documents → use discovered identifiers for additional searches → validate → stage → package → reviewer.

7. FUNCTIONAL REQUIREMENTS

FR-01 Query Intake
Accept a free-text audit request.

FR-02 Query Understanding
Use the Query Understanding Agent to convert the request into validated structured JSON.

FR-03 Use Case Classification
Classify into UC-01, UC-02, UC-03, UC-04, or UNSUPPORTED.

FR-04 Parameter Extraction
Extract relevant parameters: period, SOB, NAC range, report type, account, vendor, invoice number, sample list, and other configured identifiers.

FR-05 Requirement Catalog
Use the classified use case to retrieve its predefined required-data/document checklist. The LLM must not invent the checklist.

FR-06 Retrieval Task
Create a task containing request ID, use case, search parameters, required evidence, found evidence, missing evidence, and retry count.

FR-07 Retrieval Agent
Coordinate evidence searches across configured databases.

FR-08 MCP Layer
Expose database-search and document-retrieval operations through MCP tools.

FR-09 Sequential Database Search
Search DB-01, DB-02, DB-03, etc. in configured order. Skip evidence already found.

FR-10 Evidence Staging
Store retrieved files under evidence_staging/{request_id}/.

FR-11 Workflow State
Track raw query, parsed query, use case, parameters, evidence checklist, search attempts, found/missing evidence, validation, retries, and package status.

FR-12 Validation
Check presence, basic type/metadata match, identifier consistency, and completeness.

FR-13 Retry
Retry missing evidence using remaining databases and additional strong identifiers discovered from retrieved evidence, within a bounded retry policy.

FR-14 Package Generation
Create a final package with retrieved evidence plus machine-readable summaries.

FR-15 Human Review
Allow reviewer approval/rejection for the POC.

8. NON-FUNCTIONAL REQUIREMENTS
- Local POC only.
- Traceable workflow state.
- Structured LLM output.
- Clear progress visibility.
- Graceful error handling.
- Synthetic/mock data only.
- No authentication.
- No production deployment.

9. USER STORIES
US-01: As an auditor, I want to enter my request in normal language so I do not need technical database knowledge.
US-02: As an auditor, I want to see what the system understood before/while retrieval runs.
US-03: As an audit operator, I want the system to search multiple sources automatically.
US-04: As an audit operator, I want missing documents clearly identified.
US-05: As a reviewer, I want to review the evidence package before final release.

10. OUT OF SCOPE
- Authentication and authorization.
- Production hosting/deployment.
- Real Oracle/GROSS/DMS/SharePoint/Bank Portal connections.
- Enterprise-wide unrestricted audit-query support.
- Dynamic invention of audit methodologies or audit policies by the LLM.
- Evidence-to-System Mapping as a knowledge layer.
- Production retention/legal hold.
- Full enterprise observability.
- Automated business explanations where judgment is required.
- Final audit opinion.
- Real confidential audit data.

11. SUCCESS METRICS
- All four supported use cases can be initiated through representative natural-language requests.
- Query Understanding correctly classifies representative queries and extracts parameters.
- Correct evidence checklist is loaded from configuration.
- Retrieval Agent searches multiple SQLite databases through MCP.
- At least one test demonstrates evidence distributed across 2+ databases.
- Missing evidence is detected.
- At least one retry scenario succeeds.
- Evidence is staged per request.
- Validation returns clear COMPLETE/INCOMPLETE/NEEDS_REVIEW status.
- Reviewer approval works.
- End-to-end flow runs locally without manual backend intervention.

12. DEMO SCENARIO
Primary recommended demo:
“Provide alternate testing documents for ABC Ltd, Invoice INV-12345.”

Expected:
Auditor → Orchestrator → Query Understanding → UC-04 → Requirement Catalog → Retrieval Agent → MCP → DB-01…DB-N → Evidence Staging → Validation → Retry if needed → Package → Reviewer → Final Response.
