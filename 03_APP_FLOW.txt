DOCUMENT 03 — APP FLOW

Project: Automated Audit Evidence Retrieval
Version: 1.0

Authentication and login flows are intentionally omitted.

1. ROUTES

/ 
Redirect or landing page to the audit request screen.

/audit
Main request form.

/requests/{request_id}
Request detail/progress page.

/requests/{request_id}/review
Reviewer page.

/requests/{request_id}/package
Final package page.

/use-cases
Optional page listing the four supported use cases.

2. PRIMARY USER JOURNEY

1. Auditor opens /audit.
2. Enters natural-language audit request.
3. Clicks “Start Retrieval”.
4. Frontend POSTs the raw query to FastAPI.
5. Backend creates request ID.
6. Frontend navigates to request detail page.
7. LangGraph Orchestrator starts.
8. Query Understanding Agent parses/classifies.
9. Requirement Catalog loads expected evidence.
10. Retrieval Agent searches DBs via MCP.
11. Evidence is copied to staging.
12. Validation runs.
13. If evidence is missing, retry/re-check runs.
14. If complete, package is generated.
15. Reviewer opens package.
16. Reviewer approves/rejects.
17. Approved package becomes final response.

3. QUERY UNDERSTANDING DISPLAY

Show:
- Original Query
- Use Case ID
- Requirement Name
- Confidence
- Extracted Parameters
- Ambiguities

Example:
Query:
“Provide AP Cost Drill for August 2026, SOB 101, NAC 5000–5999.”

Understood:
Use Case: UC-01
Period: August 2026
SOB: 101
NAC: 5000–5999
Report Type: AP
Confidence: 98%

4. REQUIREMENT CHECKLIST DISPLAY

Show each required evidence item with a status:
- Pending
- Searching
- Found
- Missing
- Validated

Example UC-04:
Invoice — Found
PO — Found
GRN — Found
SES — Missing
Supporting Document — Found

5. RETRIEVAL PROGRESS

Show sequential database progress:
DB-01 → DB-02 → DB-03 → DB-04

For each:
- Searching
- Completed
- Match count
- Newly found evidence
- Error if failed

6. REVIEW SCREEN

Show:
- Original query
- Parsed query
- Required evidence
- Retrieved evidence
- Source DB for each result
- Validation checks
- Missing items
- Retry count

Actions:
Approve Package
Reject
Request Retry

7. EMPTY STATES
No requests:
“No audit requests yet. Start by entering an audit requirement.”

No evidence:
“No evidence retrieved yet.”

8. ERROR STATES

Unsupported:
“This POC supports four audit requirements: Cost Drill, Schedules, Trade Payables Balance Confirmation Samples, and Balance Confirmation Alternate Testing.”

Missing parameters:
“Required inputs are missing. Please provide the highlighted values.”

Database failure:
“Database DB-02 could not be searched. The system will continue where possible.”

No document found:
“Required evidence was not found in the searched sources.”

Parsing failure:
“The request could not be understood confidently. Please rephrase or provide the required identifiers.”

9. RETRY FLOW

1. Validation returns INCOMPLETE.
2. Orchestrator reads missing evidence.
3. Retrieval Agent receives only missing evidence plus current search context.
4. Agent searches remaining databases.
5. Agent may use related identifiers discovered from existing results.
6. Validation runs again.
7. Complete → package.
8. Still missing → NEEDS_REVIEW.

10. USE CASE FLOWS

UC-01:
Natural query → parse Period/SOB/NAC/Report Type → requirement checklist → database search → retrieve reports/data → validate → package.

UC-02:
Natural query → parse account/period → requirement checklist → retrieve balances/ageing → prepare schedule → identify long outstanding items → human explanation/review → package.

UC-03:
Natural query → parse vendor/sample/period → retrieve APTB/ageing/vendor data → generate confirmation letter → review/approval → package.

UC-04:
Natural query → parse vendor/invoice → retrieve Invoice/PO/GRN/SES/supporting documents across all DBs → validate → retry → package.

11. REDIRECTS
After submit → /requests/{request_id}
Package ready → review action
Reviewer approve → /requests/{request_id}/package
Reviewer reject/retry → request detail

12. UI POLLING
For the local POC, request detail can poll GET /api/audit-requests/{request_id} while status is active.
